# CodeMigrate benchmark: dataset card

_Generated by `python -m benchmark.dataset_card`; every number below is computed from `benchmark/cases/` and `benchmark/labels/`._

## Task

Given Python/Django source written for **Django 4.0**, find every line that breaks (raises) or emits a Django deprecation warning when upgrading to **Django 5.1**.

## Ground truth: labels from execution

Labels are produced by `benchmark/label_by_execution.py`, **not by CodeMigrate**. Each case runs under Django 4.0.10, 4.1.13, 4.2.30, 5.0.14 and 5.1.15 (Python 3.10, Docker image `benchmark/harness/Dockerfile`, no network). The driver runs Python files one statement at a time and records exceptions and `RemovedInDjango*Warning`s with file and line, plus line coverage.

* **positive line**: raises under some 4.1–5.1 release but not under 4.0, or emits a Django removal warning (removal version > 4.0) under any 4.0–5.1 release
* **ignored line** (not scored): fails already under 4.0, NameError cascade from a failed import, or failure raised inside another third-party module
* **scored lines**: lines executed under 4.0 (plus labeled spans). Findings on lines that never ran have no ground truth and are not scored
* **case status**: `ok` (used), `ambiguous` (a Django warning/error could not be attributed to a line), `silent_injection` (synthetic usage that produced no error and no warning), `invalid_source` (cannot be set up under 4.0)

Ambiguous handling: label lines come from the deepest traceback frame in the case file, the warning's own location, or, for settings modules and templates, the line naming the setting/filter in the message. When a class statement fails, the label moves to the single line inside it that the message names (e.g. `index_together`). Cases where no line can be attributed are flagged `ambiguous` and excluded from the main metrics.

## Case kinds

* **synthetic**: (a) one KB entry's API injected into small code (`kb.usage`, two styles per entry), (b) hand-written snippets for changes that need a call (`synthetic_snippets.yaml`), (c) 20 mixed files combining three snippets. The `intended` field records what the author meant to exercise and is never used as a label.
* **negative**: clean code and near-misses (replacement APIs, user-defined lookalikes, safe argument forms) in `negative_snippets.yaml`.
* **real**: files from Django-4.0-era PyPI releases (sdists pinned by version and sha256 in each `case.json` and `real_provenance.json`), selected by a plain-text grep for KB names plus randomly sampled other modules of the same package. Selection never uses the analyzer under evaluation.

## Splits

`dev` (~30%) / `test` (~70%), assigned by hashing a group key with seed 42: all variants of one API, all files of one package, and each snippet stay in one split. Development and debugging use `dev`; reported numbers use `test`.

## Rebuild

```bash
python -m benchmark.build_benchmark          # cases (downloads pinned sdists)
python -m benchmark.label_by_execution       # Docker; labels/
python -m benchmark.dataset_card             # this file
```

## Limitations

* Execution only observes executed paths: usages inside functions that are never called are unscored. Real-code labels are mostly import-time and class-definition breakages.
* Behavior changes (same API, different semantics) are not labeled; `behavior_changed` KB entries are out of scope for this benchmark.
* Some documented removals are silent at runtime (e.g. removed settings are ignored). By the execution definition they are not breaking; systems that flag them are counted as false positives unless the earlier release emitted a warning.
